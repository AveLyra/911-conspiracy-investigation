## Result

The public saved Camera 3 project contains a **concrete configured metric calibration**: a 58.293 m assigned tape, fixed equal x/y scale of 3.3366687576783383 pixels per assigned metre, and a saved 0.7240787271407187-degree axis angle. Its tape endpoints reproduce that scale internally. Therefore “there is no calibration” would be false. The project can support conditional image-to-assigned-world conversion under its declared geometry and clock assumptions.

The missing link is independent validation of the tape's physical endpoints/reference length, projection and original analysis/exposure clock—not the existence of useful settings. A configured metre is not automatically an authenticated metre in the pictured building. Camera 2's different file/view/raster and newly defined outline points cannot inherit Camera 3's scale merely by a “WTC 7” or camera label.

The existing timing and cadence work supplies both positive evidence and limits. Encoded clocks are recoverable exactly, and the saved software units are identifiable. The shorter Camera 3 copy also has a reproducible near-neighbor pattern. That pattern supports a recording-process concern but does not determine a unique time correction. The later WMV diagnostic places its three warnings in countdown graphics, outside the saved PointMass selections; those warnings do not demonstrate corrupted collapse measurements. Missing custody cannot be converted into an assumed clock distortion or a reason to discard all conditional inference.

## What the saved metric calibration actually establishes

The original TRK hash is `955d1c2d00d7c287f4f235063eb603a0080cf0941595a5419aa7c94726c1a41c`. Its selected settings derivative hash is `ccfd9c4de098539680caf9f296eb5ea784ade27497d860a32284285e577cefeb`.

The saved tape has endpoints (414.3770672546858,196.24035281146615) and (416.95700110253586,390.7276736493937), with assigned world length 58.293 and length-unit label `m`. A read-only configuration check gives a pixel endpoint distance of 194.50443189134342; division by 58.293 gives 3.336668757678339 pixels per assigned metre, matching the stored 3.3366687576783383 to rounding. Its reciprocal is approximately **0.29970011188518525 assigned m/pixel**. This internal equality is expected from a tape-set transform; it is not an independent confirmation of the assigned physical length.

The origin is (515.7950065703022,400.52562417871223), and origin/angle/scale are saved as fixed. The source serializer writes the angle in degrees and the loader converts it to radians. Image y increases downward; the zero-angle world-Y convention reverses that sign. Neither fixed flags nor equal x/y scale establish a stationary camera, known depth, orthographic projection or whole-building rigidity.

The prior kit review states that the floor-spacing sheet supplies floor elevations/increments but no drawing identifier or demonstrated visible tape endpoint assignment. Its source PDF is pinned there at `8dacd6cbb61b554c21da2cfa6447ebbb3248a06d04a44596b5c31088e5beb411`. The lab instructions, source hash `c3a9c7aa44f914dbcc7dd2e5604020db0466de8c27f9d71f70d485b80aeb5557`, describe using floor spacing and rotated axes. These are affirmative calibration leads. They are not no-evidence, and this pass does not newly inspect their page images or decide the visible endpoints' identities.

NIST's reported descent calibration uses architectural elevations for a particular parapet/occlusion feature, while its detailed point is described near the roofline center. Appendix C's marker instead converts **vertical movement of an intensity-intersection marker into horizontal edge vibration**, using the reported façade width. That horizontal amplification/calibration cannot be applied to vertical roof descent. Nor can any of those Camera 3 observables be equated with the Camera 2 T1/T2 right-side outline definitions without geometry and source correspondence.

## Clock units, rate and source semantics

Relevant positive source findings:

1. Saved `delta_t=66.66666666666667` is a **mean frame duration in milliseconds** in the inspected tagged 6.1.2 controller. Saved `rate=1.0` controls playback scheduling; it is not the analysis-time multiplier.
2. Saved start frame 138, step size 3 and step count 102 request indices 138,141,…441. The two PointMass tracks have only 71 saved marked indices each, ending at 348. Selection extent is not annotation coverage.
3. For the valid-video path, the controller rescales existing engine frame-time differences. If engine times are uniform and the saved finite settings load without override, the selected spacing is nominally 0.2 s. That is conditional configuration arithmetic, not a newly measured exposure interval.
4. `VideoPlayer.getStepTime()` includes the assigned clip start time and follows stretched controller times. The inspected PointMass path divides this result by 1000 for seconds. The different `getFrameTime()` API uses mean-duration arithmetic and can differ internally on an irregular engine clock.
5. Saved `starttime=0` is an assigned analysis origin. It is not absolute PTS zero, the time of a support failure, or an independent synchronization observation.

For finite valid-video endpoints a,b, let p[n] be the engine's millisecond frame-time array and d the assigned mean duration. The audited path uses S=d(b−a)/(p[b]−p[a]) and step times `{t0+S[p[a+3k]−p[a]]}/1000`. The historical Xuggle-populated p[n], loaded file/endpoints, exact executable/dependency identity and any runtime time-source overrides remain unverified. Therefore current FFprobe PTS must not be silently relabeled as the original application's engine array.

Those missing dependencies do **not** prove that the engine clock was wrong. A historically uniform, correctly scaled clock remains a live conditional model consistent with these settings. The protocol can study what follows under that explicit model without claiming to have authenticated it or substituting a favored correction.

Constant event-origin offsets, affine clock-rate changes and nonlinear within-clip timing are different issues. The source records identify some assigned offsets and nominal durations; they do not measure an arbitrary historical clock-rate error. The main analytic unit handles their distinct mathematical consequences. No synthetic clock distortion is asserted to have occurred here.

## Finite next tests and disposition

**Admit now, with labels:** native-coordinate observations tied to exact file PTS; published-method attribution; saved-program unit/transform semantics; and explicit conditional physical-unit/sensitivity calculations tied to a named source, feature and geometry/clock assumption.

**Do not label as established from this unit:** a unique exposure history, a corrected clock, cross-camera metric transfer, exact material continuity, a new gravity-compatible historical interval, whole-building force/mass behavior or a cause. This is a scope/evidence distinction, not a presumption favoring either fire or deliberate intervention.

The highest-value calibration test is to identify the saved tape's visible endpoints in its actual referenced media and tie them to a specific independently sourced dimensional drawing/reference, preserving endpoint and projection uncertainty. The corresponding clock test is the original permitted exported point/time table plus exact loaded media/engine state, compared row-by-row against the source-time chain; a fresh nominal-FPS table is not equivalent. Those are prospective scoped tests, not authorization to run the kit, acquire unavailable materials, or revisit restricted productions.

Main's separately declared primary-page geometry review and independent mathematical review can refine the conditional admissibility decision. They must not be counted as already completed by this source note. The investigation's other workstreams remain open, and this task does not narrow any legal discovery or production review.
